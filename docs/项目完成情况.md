# JourneyCraft — 项目完成情况与技术文档

> 北京昌平区智能旅行规划平台 | 数据结构课程设计项目

---

## 一、项目概述

JourneyCraft 是一个面向北京昌平区的智能旅游规划平台，覆盖**景点浏览、餐馆查询、游记撰写、室内导航、AI 行程助手、预算管理**六大核心功能模块。项目采用前后端分离架构，以真实地图数据（高德 POI + OSM 路网）为基础，自实现 Dijkstra、TSP、Top-K MinHeap、Levenshtein、Deflate 等核心算法。

**数据规模**：
- 210 个景点（高德 API 真实昌平区 POI）
- 337 家餐馆（高德 API 真实餐馆 POI）
- 337+ 服务设施（12 个分类）
- 267,094 个 OSM 路网节点 + 540,956 条边
- 5 层建筑物室内导航图（575 个节点，570 条同层边，16 条跨层边）

## 四、核心算法清单

### 4.1 路径规划算法

#### Dijkstra 最短路径

| 属性 | 说明 |
|------|------|
| **文件** | `DijkstraAlgorithm.java` |
| **复杂度** | O((V+E)logV) |
| **自实现** | ✅ 全部手写（二叉堆优先队列） |
| **选型原因** | 昌平路网 54 万条边，99% 正向距离。A* 需要启发函数（额外维护成本），Bellman-Ford 太慢（O(VE)），Floyd-Warshall 内存爆炸（O(V³)）。Dijkstra 是正权图最优解 |
| **应用场景** | ① 单目标最短路径规划 ② 附近设施步行距离计算 ③ 室内 Dijkstra（分层图跨层导航） |

**拥挤度加权**：真实速度 = 道路基速 × 拥挤系数（HIGH=0.4 / MEDIUM=0.7 / LOW=1.0）。TIME 策略下，每条边的权重 = distance / effectiveSpeed。

**多交通方式**：支持 WALK(5km/h) / BIKE(15km/h) / SHUTTLE(30km/h)，每种交通方式独立跑 Dijkstra，选时间最短路径。

**道路类型过滤**：GraphEdge.isAllowedForTransport() 按交通方式过滤道路类型：
- WALK：禁止 motorway/trunk
- BIKE：禁止 motorway/trunk/steps
- SHUTTLE：禁止 footway/path/pedestrian/steps/cycleway

**连通分量桥接**：OSM 路网存在 840 个连通分量。自动检测不同分量 → 哈弗辛距离找最近节点对 → 插入步行过渡段 → 拼接路径。

**网格空间索引**：Graph.buildGridIndex() 将 267k 节点分入 9 个网格单元，findNearestNode 从全局 O(N) 降至 O(1)。

#### TSP 旅行商问题

| 属性 | 说明 |
|------|------|
| **文件** | `TSPAlgorithm.java` |
| **算法** | 贪心初始化 + 2-opt 局部优化 |
| **复杂度** | O(n²) 贪心 + O(n²) 每轮 2-opt |
| **自实现** | ✅ 全部手写 |
| **选型原因** | 旅游场景 n≤20，精确解 Held-Karp DP 为 O(2ⁿ·n²)（1024×100），贪心+2-opt 几毫秒出结果，路径质量接近最优（差距 <5%） |

**支持**：指定终点（finalDestinationIdx），开放路径而非闭合回路。

### 4.2 排序与查找算法

#### Top-K 最小堆排序

| 属性 | 说明 |
|------|------|
| **文件** | `TopKSorter.java` |
| **复杂度** | O(N logK)，空间 O(K) |
| **自实现** | ✅ 全部手写（MinHeap 类，含 siftUp/siftDown） |
| **选型原因** | 用户只看 Top 10，"全量排序再取前 10"是 O(N logN)。固定容量最小堆只维护 K 个元素，数据动态增长时差距显著。对照评分标准："不经过完全排序可以排好前 10" |

**应用场景**：景点推荐 Top 10、餐馆推荐 Top 10、推荐引擎多样性重排。

#### Levenshtein 编辑距离 + Trie 前缀树

| 属性 | 说明 |
|------|------|
| **文件** | `FuzzyMatcher.java` |
| **复杂度** | 编辑距离 O(m·n)（滚动数组优化至 O(min(m,n))），Trie 查询 O(L) |
| **自实现** | ✅ Trie 和 Levenshtein 全部手写 |
| **选型原因** | 用户输入"十三岭"应能搜到"十三陵"。编辑距离比 SQL LIKE 更容错，Trie 比 HashMap 更高效前缀匹配 |

### 4.3 推荐算法

#### 多信号加权融合推荐引擎

| 属性 | 说明 |
|------|------|
| **文件** | `SpotRecommendationEngine.java`（383 行） |
| **信号源** | ① 用户兴趣标签（32% 权重）② 用户收藏类别亲和度（10%）③ 用户浏览类别亲和度（8%）④ 景点热度（22%）⑤ 景点评分（18%）⑥ 旅游优先级（5%） |
| **归一化** | 热度用 log1p 压缩（避免 1500 vs 200 的极端差异垄断），评分用置信度加权（≤50 人评分打折扣） |
| **多样性重排** | Top(K×3) 取高分池 → 每类最多 2-3 个 → 强制混入不同类别 |
| **群组推荐** | 支持多用户兴趣交集优先、并集兜底 |

### 4.4 压缩算法

#### Deflate 无损压缩

| 属性 | 说明 |
|------|------|
| **文件** | `DiaryCompressor.java` |
| **算法** | LZ77 + Huffman（原始 Deflate，不带 GZIP 头） |
| **自实现** | 使用 Java `java.util.zip.Deflater`，自封装压缩/解压逻辑 |
| **压缩比** | 3~8x |
| **选型原因** | 游记富文本 10KB+，压缩到 1-3KB。Deflate 是 ZIP 核心但省去文件头/校验和开销。文本场景比 LZ4（重速度）好，比 Brotli（重比）快 |

**特色**：懒压缩迁移——已有数据不解压重存，访问时检测未压缩的 contentHtml 自动压缩。

### 4.5 室内导航

| 属性 | 说明 |
|------|------|
| **文件** | `IndoorNavigationService.java` |
| **算法** | 分层 Dijkstra（同层 Dijkstra + 跨层电梯/楼梯边） |
| **数据** | MongoDB 存储，每层 100+ 节点，575 节点/570 同层边/16 跨层边（共 5 层） |

**跨层机制**：CrossFloorEdge 连接不同楼层的电梯/楼梯节点，Dijkstra 在包含跨层边的图上寻路，自动规划"F1→F2→F3"路径。

## 八、智能体开发流程

本项目完全通过 AI 智能体辅助开发，使用 OpenCode 平台的多智能体体系：

| 智能体 | 职责 | 使用场景 |
|--------|------|---------|
| **Sisyphus（本对话）** | 编排者，需求理解→任务分解→委派→验证 | 全程 |
| **explore** | 代码库探索，模式查找 | 每次新需求先搜索现有实现 |
| **plan** | 任务分解，并行执行图生成 | 多步骤复杂任务 |
| **oracle** | 架构咨询，困难调试 | 复杂逻辑审查 |
| **visual-engineering** | 前端 UI 实现 | 视觉相关改动 |
| **quick** | 简单单文件修改 | 一行改动 |

**开发模式**：
1. 需求分析 → 理解真实意图
2. 并行探索（2-5 个 explore agent）→ 收集上下文
3. Plan agent 生成任务图 → 确定执行顺序
4. 委派执行 → 逐任务完成
5. 验证（vue-tsc + vitest + .mvnw test）→ 确保无回归

## 十二、已知局限与后续方向

| 局限 | 说明 |
|------|------|
| OSM 路网有时不连通 | 昌平区有 840 个连通分量，自动桥接但非真实道路连接 |
| 室内导航无真实平面图 | 节点坐标由脚本自动生成，非从 CAD/图片提取 |
| 没有单元测试覆盖新功能 | 推荐引擎、预算模块、收藏/历史等缺少测试 |
| AI 生成内容不稳定 | DeepSeek 输出格式有时不严格，需要后处理 |
| 菜系分类不完整 | 前端按钮与数据库值不一一对应，使用 LIKE 模糊匹配做兼容 |
| 前端有大量旧 `.js` 文件 | Vite 优先解析 `.ts` 但热更新可能出错，已全部删除 |
